# Phase 3 — API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build BACKEND's FastAPI endpoint surface (`/status`, `/requests`, `/stats`, `/pricing` + `/pricing/refresh`, `/db/tables`), wiring Phase 2's collector/DB to Phase 1's DATE-TIME and PRICING-ENGINE. `POST /control/*` is explicitly deferred to Phase 4.

**Architecture:** One FastAPI app (`backend/src/fcc_dashboard/api.py`) with a startup hook that calls `init_db` once and stores the connection on `app.state.db` (a single shared connection — WAL mode + `check_same_thread=False`, hardened in Phase 2 specifically for this). Route handlers are grouped into per-concern modules (`routes_status.py`, `routes_requests.py`, `routes_stats.py`, `routes_pricing.py`, `routes_db.py`) that the app assembles as FastAPI routers, keeping each file focused and independently testable via `fastapi.testclient.TestClient`.

**Tech Stack:** FastAPI, `httpx` (already a dev dependency from Phase 0; promoted to a runtime dependency here since the app itself needs it for FCC's `/health` check and the LiteLLM/OpenRouter fetches), pytest + `fastapi.testclient.TestClient`.

**Spec:** `vault-fcc-dashboard/plans/PHASE-3-API.md`, `vault-fcc-dashboard/features/BACKEND/BACKEND--api.md`, `BACKEND--architecture.md`, `DATE-TIME/DATE-TIME--architecture.md`, `PRICING-ENGINE/PRICING-ENGINE--architecture.md` + `--price-refresh.md`.

## Global Constraints

- All routes are read/write against `app.state.db` (the Phase 2 `init_db` connection) — no new connections opened per-request.
- **Ruling (carried forward from Phase 2, resolved now):** `/stats`'s cost aggregation only includes rows with `status = 'completed'` AND non-NULL `input_tokens`/`output_tokens` — `pending`/`error` rows are counted toward request/usage totals but never fed into `compute_cost`/`compute_savings` (which assume real token counts). This is the None-guard Phase 2's review flagged as needed before Phase 3 calls PRICING-ENGINE.
- **Ruling (carried forward, resolved now):** a row with `gateway_model IS NULL` (an orphan `completed` row with no prior `request.sent`) is treated as "unknown pricing" at the API layer — checked and excluded *before* calling `compute_savings`, which still raises `ValueError` for its original, narrower case (a real, non-NULL `gateway_model` value that isn't a configured Anthropic tier — a genuine config error, not a data gap).
- **Ruling (carried forward, resolved now):** `/stats`'s range parameter uses exactly the four ranges Phase 1's `resolve_range_boundaries` already supports (`today`, `last_7_days`, `last_30_days`, `all_time`) — no calendar-month range added. YAGNI: nothing in the vault specifies a calendar-month requirement, and the rolling-window function already exists and is tested; add a new range later if a real need surfaces.
- **Ruling (new, this phase):** the pricing config file lives at `~/.fcc-dashboard/pricing.json` (a user-level config directory, mirroring FCC's own `~/.fcc/` convention — this repo already models its whole design on FCC's structure). If the file doesn't exist on first `GET /pricing` or `POST /pricing/refresh`, it's created with a seeded default containing real Anthropic Opus/Sonnet/Haiku prices (so `compute_savings` never fails purely because the file never existed) and an empty `providers` object.
- FCC's own health endpoint is `GET http://localhost:8082/health` (confirmed in `current-task.md`'s FCC facts) — used by `GET /status`. A short timeout (e.g. 2 seconds) is required so a down/unreachable FCC doesn't hang the status endpoint.
- Down/stale-key/rate-limit classification (locked earlier in this project): `http_status` 401/403 -> `stale_key`, 429 -> `rate_limited`, 5xx or a timeout/connection error -> `down`. Anything else (or no recent error) -> `ok`.

**Contract for `GET /status`:**
- Response shape: `{"fcc_status": "up" | "down", "providers": [{"provider": str, "status": "ok" | "stale_key" | "rate_limited" | "down", "last_error_at": str | null, "http_status": int | null}]}`.
- `fcc_status` is `"up"` if `GET http://localhost:8082/health` returns HTTP 200 within a 2-second timeout; `"down"` for any other response, timeout, or connection error (never raises out of the route — a down FCC is an expected, normal state to report, not a server error).
- `providers`: one entry per distinct `provider` value that appears in any `error`-status row in `requests`, using each provider's MOST RECENT error row (by `occurred_at`) to classify status via the locked http_status rule above. Providers with no error rows at all are not included in this list (there's nothing to report — "no news" isn't the same as "ok" when we don't even know if that provider has been used).
- Must work against an empty `requests` table (no providers reported, `providers: []`) without erroring.

### Task 3: `GET /stats`

**Files:**
- Create: `backend/src/fcc_dashboard/routes_stats.py`
- Modify: `backend/src/fcc_dashboard/api.py` (include the new router)
- Test: `backend/tests/test_routes_stats.py`

**Interfaces:**
- Consumes: `get_db` (Task 1), `resolve_range_boundaries` (Phase 1 `datetime_utils`), `compute_savings`/`load_pricing_config` (Phase 1 `pricing`).
- Produces: a `GET /stats` route.

**Contract:**
- Query param: `range` — one of `today`, `last_7_days`, `last_30_days`, `all_time` (use a FastAPI `Literal`/`Enum` type so an invalid value is a 422). Default `last_7_days`.
- Resolves the range via `resolve_range_boundaries(range_name)` (no `local_tz`/`now` overrides — production always uses the real host time, per DATE-TIME--architecture) to get `(start, end)` UTC ISO-8601 boundaries, then queries `requests` for rows where `occurred_at BETWEEN start AND end` (inclusive both ends, per DATE-TIME's documented convention).
- Loads the pricing config via `load_pricing_config` (reading the same `~/.fcc-dashboard/pricing.json` path as Task 4 will use for `GET /pricing` — if the file doesn't exist yet, treat this as "no pricing data available" and return `total_savings: null`, `unpriced_request_count` equal to the completed-row count, rather than erroring; don't create the file from this read-only endpoint).
- For every row with `status = 'completed'` and non-NULL `input_tokens`/`output_tokens` AND non-NULL `gateway_model` (per this plan's Global Constraints ruling), call `compute_savings`. Sum `savings` across all rows where `unknown=False`. Count rows where `unknown=True` (or missing gateway_model, or missing tokens) separately as `unpriced_request_count` — never silently treat them as $0.
- Response shape:
```json
{
  "range": "last_7_days",
  "range_start": "2026-08-17T00:00:00.000Z",
  "range_end": "2026-08-24T12:00:00.000Z",
  "total_requests": 42,
  "completed_requests": 38,
  "error_requests": 3,
  "pending_requests": 1,
  "total_input_tokens": 123456,
  "total_output_tokens": 78910,
  "total_savings": 12.34,
  "unpriced_request_count": 2,
  "by_provider": [{"provider": "nvidia_nim", "request_count": 20, "savings": 8.5}, ...]
}
```
`total_savings` is `null` (not `0`) if there is no pricing config file at all (never priced anything, ever) — distinct from a legitimate `0.0` (priced everything, savings genuinely summed to zero). `by_provider` groups only rows with a non-NULL `provider`.

**Contract:**

Response: `{"table": name, "total": int, "limit": int, "offset": int, "columns": [str, ...], "rows": [[...], ...]}` (rows as arrays matching `columns`' order — this is a raw debug view, not a semantic one). If `name` isn't a real table (or isn't in the `sqlite_master` list from the other endpoint), return HTTP 404, not a 500 or an empty result — and critically, validate `name` against the actual table list before using it in a query (never interpolate the path parameter directly into SQL — table/column names can't be parameterized with `?` placeholders in SQLite, so the safe pattern is: look up the real table name from `sqlite_master` first, then use it only if it's an exact match).
